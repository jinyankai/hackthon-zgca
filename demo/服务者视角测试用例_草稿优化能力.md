# 服务者视角测试用例：草稿优化与服务者保护能力测试

## 测试目标

用于验证模型是否真的能把服务者在高压状态下写出的草稿，优化成“真人专业腔”的回复，而不是机械客服模板。

模型应该做到：

1. 去除服务者草稿中的攻击、敷衍、甩锅、过度自责和不当承诺。
2. 保留服务者能做的具体动作。
3. 让回复听起来像真实的人，而不是客服八股文。
4. 明确边界，不替企业乱承诺。
5. 在服务者自责、害怕投诉、被辱骂时保护服务者。
6. 输出修改理由，让服务者知道为什么这样改。
7. 保留人工确认，不自动发送。

## 推荐输出结构

每条服务者草稿建议输出以下字段：

```json
{
  "polished_text": "",
  "tone": "calm | firm | empathetic | boundary | urgent",
  "changes_summary": [],
  "removed_risks": [],
  "missing_info": [],
  "agent_boundary_tip": "",
  "should_escalate": false,
  "approval_needed": true
}
```

## 风格要求：真人专业腔

### 避免默认使用

- 您好
- 感谢您的反馈
- 感谢您的理解和耐心
- 请您放心
- 我们会尽快处理
- 相关流程
- 给您带来不便深表歉意
- 我们非常重视

这些词不是绝对不能用，但不能作为默认模板。

### 推荐风格

- 具体
- 短句
- 承认现实
- 给出下一步动作
- 不乱承诺
- 不卑微
- 不甩锅
- 有边界

## 用例 1：生硬拒绝退款

### 服务者草稿

```text
退款不是我说退就退的，要走流程，你催也没用。
```

### 上下文

客户因配送严重延迟，要求退款并威胁投诉。

### 期望输出要点

```json
{
  "polished_text": "我理解您现在是想尽快确认能不能退款。退款确实需要先看订单状态和平台规则，我现在先帮您查这两个信息：订单是否已出库，以及是否符合退款条件。查到后我会直接告诉您能退、不能退，或者还需要补充什么信息。",
  "tone": "firm",
  "changes_summary": [
    "去掉了“你催也没用”的对抗表达",
    "保留了退款需要按规则确认的边界",
    "补充了具体查询动作"
  ],
  "removed_risks": ["激化矛盾", "服务态度生硬"],
  "missing_info": ["订单状态", "退款规则适用条件"],
  "agent_boundary_tip": "不要承诺一定退款；先确认订单状态和规则。",
  "should_escalate": false,
  "approval_needed": true
}
```

### 重点检查

- 不能输出“请您放心，我们会尽快为您办理退款”。
- 必须保留“退款不能由服务者直接决定”的边界。
- 要有具体动作：查订单状态、查退款条件。

## 用例 2：敷衍式回复

### 服务者草稿

```text
知道了，我问一下。
```

### 上下文

客户重复追问订单是否有人处理，已经表现出焦虑。

### 期望输出要点

```json
{
  "polished_text": "我现在帮您确认具体进展。查到后我会告诉您两件事：目前卡在哪一步，以及接下来能怎么处理。",
  "tone": "calm",
  "changes_summary": [
    "把敷衍表达改成明确动作",
    "补充客户接下来会得到的信息",
    "避免空泛安抚"
  ],
  "removed_risks": ["客户觉得被敷衍", "继续重复追问"],
  "missing_info": ["当前处理进展", "下一步处理路径"],
  "agent_boundary_tip": "如果暂时查不到结果，应给出下一次反馈时间。",
  "should_escalate": false,
  "approval_needed": true
}
```

### 重点检查

- 不要变成“感谢您的反馈，我会马上为您询问相关信息”。
- 要说明查什么、会反馈什么。

## 用例 3：甩锅系统

### 服务者草稿

```text
这破系统又崩了，我也没办法啊，你等着吧。
```

### 上下文

客户正在等待退款处理，但后台系统暂时异常。

### 期望输出要点

```json
{
  "polished_text": "目前系统确实出现异常，我现在暂时不能直接完成这一步操作。我会先记录您的问题和订单信息，等系统恢复后优先继续处理；如果您愿意，也可以先把订单号发我，我先确认需要补充的信息。",
  "tone": "transparent",
  "changes_summary": [
    "去掉了“破系统”“我也没办法”的甩锅表达",
    "保留系统异常这一事实",
    "补充系统异常期间仍能做的动作"
  ],
  "removed_risks": ["显得不专业", "把内部问题直接甩给客户", "让客户觉得只能空等"],
  "missing_info": ["订单号", "系统恢复时间"],
  "agent_boundary_tip": "不要承诺系统恢复时间；可以说明当前限制和可先做的准备动作。",
  "should_escalate": false,
  "approval_needed": true
}
```

### 重点检查

- 不能只说“我们正在努力解决，请耐心等待”。
- 必须说明系统异常下还能做什么。
- 不能承诺无法保证的恢复时间。

## 用例 4：过度自责求客户别投诉

### 服务者草稿

```text
对不起对不起，都是我的错，我马上处理，求您别投诉我。
```

### 上下文

客户威胁投诉，但问题原因尚未确认。

### 期望输出要点

```json
{
  "polished_text": "我理解您现在很不满，我会先把这件事处理起来。为了避免耽误，我先确认订单和问题原因；查清楚后会告诉您目前能怎么解决。投诉是您的权利，但我会先尽力把当前问题推进。",
  "tone": "calm",
  "changes_summary": [
    "移除了过度自责和求饶表达",
    "避免服务者承担未确认责任",
    "保留了愿意处理问题的态度"
  ],
  "removed_risks": ["服务者背锅", "过度承诺", "情绪失控"],
  "missing_info": ["具体问题原因", "订单信息", "可处理方案"],
  "agent_boundary_tip": "服务者不需要把未确认的问题归为自己的错，也不需要请求客户不要投诉。",
  "should_escalate": false,
  "approval_needed": true
}
```

### 重点检查

- 必须保护服务者边界。
- 不要说“都是我们的错”。
- 不要否认客户投诉权利。

## 用例 5：服务者被辱骂后想反击

### 服务者草稿

```text
你说话能不能客气点？又不是我让你等这么久的！
```

### 上下文

客户因超时等待辱骂服务者。

### 期望输出要点

```json
{
  "polished_text": "我会先帮您处理订单延迟的问题。为了更快解决，我现在需要确认订单状态和预计送达时间；如果您继续使用攻击性表达，我会请主管一起介入处理。",
  "tone": "boundary",
  "changes_summary": [
    "去掉了反击式表达",
    "把焦点拉回订单延迟问题",
    "加入了清晰但不激化的边界"
  ],
  "removed_risks": ["冲突升级", "互相攻击", "服务者被继续消耗"],
  "missing_info": ["订单状态", "预计送达时间"],
  "agent_boundary_tip": "面对辱骂时不需要继续单独承接，应使用边界话术并可升级主管。",
  "should_escalate": true,
  "approval_needed": true
}
```

### 重点检查

- 不能只改成卑微道歉。
- 必须保留服务者边界。
- 必须提示可升级主管。

## 回归测试检查清单

每次模型更新后，至少检查以下问题：

- [ ] 是否从客服模板腔变成人类专业表达？
- [ ] 是否给出具体动作，而不是“尽快处理”？
- [ ] 是否避免不当承诺？
- [ ] 是否保护服务者不背未确认责任？
- [ ] 是否保留必要边界？
- [ ] 是否在辱骂、悲伤、医疗、群体性事件中建议升级？
- [ ] 是否输出修改理由？
- [ ] 是否说明缺失信息？
- [ ] 是否要求人工确认发送？
- [ ] 是否避免“感谢您的反馈、请您放心、请耐心等待”等机械套话？
